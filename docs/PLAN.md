## 2. 기준선 (Mission 0 에서 측정)
| 대상 | 테스트 수 | 줄 커버리지 | 변이 점수 |
|---|---|---|---|
| ai_tests | 39 (39 통과 / 0 실패) | 97.57% (분기 81.34%) | 58.2% (110/189) |

해석: 줄 커버리지는 97.6% 이지만 변이 점수는 58.2% 이다. AI 테스트는 코드를 실행하기만 하고 결과를 충분히 확인하지 않아, 심어 둔 결함 10개 중 약 4개를 놓친다. 생존 변이체가 많은 파일: payment.js 20개, cancel.js 14개, cart.js · orderQuery.js · expiry.js 각 11개.

## 3. 작업 계획
| 미션 | 쪼갠 작업 단위 | 확인 방법 | 예상 위험 |
|---|---|---|---|
| M1 | 계약서 규칙 하나(동등분할 그룹 하나)씩 케이스 목록 작성 → 승인 → 테스트 작성 | 케이스 목록을 계약서와 대조, npm test 통과, 일부러 틀린 값으로 실패 확인 | 에이전트가 src 코드를 보고 기대값을 베낌 / 경계값 누락 |
| M2 | ai_tests 파일 하나씩 약한 단언 · 잘못된 기대값 찾기 → 개선 테스트 작성 | TEST_REVIEW 에 위치와 근거 기록, 개선 후 변이 점수 비교 | ai_tests 를 직접 수정해 버림 / 약점을 놓침 |
| M3 | 성공 → 실패 → 시간 초과 → 재시도 → 동시 요청 순서로 단계 분리 | 모의 PG 로 각 경로 실행, 사유 값(reason)까지 단언 | 성공 경로만 테스트됨 (payment 생존 20개, cancel 14개) |
| M4 | flaky 테스트 하나씩 원인 찾기 → 수정, 그다음 ci.js 완성 | repeat 30회 모두 통과, CI 가 my_tests 는 통과 · ai_tests 는 실패 | 단언을 약하게 만들어서 "고친 척" 하게 됨 |
| M5 | 생존 변이체 하나씩 진짜 결함 / 동등 변이체 판단 → 죽이는 테스트 추가 | npm run mutate 로 변이 점수 상승 확인 | 시간 경계(밀리초) · 상태 조합 누락 |

## 4. 안전장치 (우리 팀이 지킬 것 3가지)
1. 에이전트 작업이 끝날 때마다 git status 로 src/ · ai_tests/ 변경 여부를 확인하고, 변경되었으면 git checkout -- src ai_tests 로 되돌린다.
2. 에이전트에게는 먼저 테스트 케이스 목록만 받고, 내비게이터가 계약서와 대조해 승인한 뒤에만 코드를 쓰게 한다.
3. 커밋 전에 npm test 를 3번 실행해 실패 0개 · 결과 동일을 확인하고, AI_USAGE_LOG 는 미션이 끝날 때마다 바로 쓴다.
