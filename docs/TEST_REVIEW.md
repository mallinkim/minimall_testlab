# AI 가 만든 테스트 리뷰 노트 (Mission 2)

대상: `ai_tests/*.test.js` (AI 도구가 생성했다고 가정). 기준: SRS · 계약서.
먼저 **측정**한다: `npm run coverage -- --tests ai_tests` 와 `npm run mutate:ai`. 그 다음 읽는다.

## 점검 체크리스트 (확인한 항목에 표시)
- [x] 단언이 값을 비교하는가? (`assert.ok(x)` · 존재 여부 · 길이만 확인하지 않는가)
- [x] 기대값이 독립적인가? (결과로 기대값을 계산하는 동어반복이 아닌가)
- [x] 경계값이 있는가? (최소 · 최대 · 딱 맞는 값 · 바로 바깥)
- [x] 오류를 제대로 확인하는가? (오류 코드까지 확인하는가, `try/catch` 로 삼키지 않는가, 오류가 안 나도 통과하지 않는가)
- [x] 테스트 이름과 단언이 일치하는가?
- [x] 테스트가 독립적인가? (한 테스트만 실행해도 통과하는가: `node scripts/test.js ai_tests --name "<테스트 이름>"`)
- [x] 계약서의 실패 경로 · 동시성 · 권한 규칙이 빠져 있지 않은가?
- [x] 같은 것을 반복하거나 구현 세부(저장소 내부 구조)에 묶여 있지 않은가?

위 수치는 Mission 2 시점 값이다. 최종 수치(179개, 변이 98.4%)는 TEST_REPORT.md에 있다.

변이 점수가 오른 이유: 줄 커버리지는 둘 다 거의 100%라 차이가 작지만, 우리 테스트는 결과를 값으로 비교하고(오류 코드 · details · 금액), try/catch 로 오류를 삼키지 않으며, 실패 후 바뀌지 않아야 할 것까지 확인한다. 그래서 같은 줄을 실행해도 결과가 달라지면 실패한다. 특히 payment.js 는 15/35 → 30/35 로 올라, 결제 실패를 성공으로 처리하는 결함(payment#9 · #10 · #13)과 취소된 주문 결제(payment#21)를 이제 잡는다. 남은 생존 변이체 15개는 동시 요청 중복 방지(payment#24, cancel#18), 조회 권한(orderQuery#1 · #4), 자동 취소 상태 조건(expiry#2) 등으로 M3 · M5 에서 다룬다.

## 팀의 결론 (3~5문장): AI 가 만든 테스트를 어떻게 믿을 수 있게 만들 것인가?
- AI 테스트는 39개가 모두 통과하고 줄 커버리지가 97.6% 였지만 변이 점수는 58.2% 로, "통과한다"와 "결함을 잡는다"는 다른 것이었다.
- 특히 try/catch 로 오류를 삼킨 테스트와 결과로 기대값을 다시 계산한 테스트는 실패할 수 없는 테스트였고, 이를 변이 도구로 실행해 확인했다.
- AI 테스트를 믿으려면 기대값을 계약서에서 미리 계산해 고정하고, 오류는 코드와 details 까지, 실패 후 바뀌지 않아야 할 것까지 단언하게 해야 한다.
- 또 케이스 목록을 사람이 계약서와 대조해 승인한 뒤에만 코드를 쓰게 하고, 새 테스트는 검증자가 일부러 틀린 값으로 실패시켜 본 뒤에 받아들인다.
- 그 결과 변이 점수가 92.1% 로 올랐지만 동시성 · 조회 권한 결함이 남아 있어, 변이 점수는 완벽함의 증거가 아니라 다음에 볼 곳을 알려 주는 지표로 쓴다.
