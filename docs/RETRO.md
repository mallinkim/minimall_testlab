# 팀 회고

1. AI 가 만든 테스트를 '믿어도 되는가'를 판단할 때, 우리 팀이 가장 도움이 된 지표(또는 방법)는 무엇이었나요? (구체적 사례)
- (김윤영) 변이 점수와 "일부러 틀린 값으로 실패시켜 보기"가 가장 도움이 되었다. ai_tests 39개는 모두 통과하고 줄 커버리지도 97.57% 였지만 변이 점수는 58.2% 였다. 제공된 변이 도구를 payment · cart 로 좁혀 돌려 보니, 결제 실패를 성공으로 처리하는 결함(payment#10 · #13)과 취소된 주문을 결제하는 결함(payment#21)이 살아남았다. 즉 try/catch 로 오류를 삼킨 테스트는 실패할 수 없는 테스트였다. 반대로 우리가 고친 TC-R-19 는 failNextCharge 줄을 지우자 바로 실패해, 같은 시나리오를 실제로 검사한다는 것을 확인했다.
- (곽민주) 

2. 줄 커버리지와 변이 점수가 다르게 나왔을 때 무엇을 배웠나요?
- (김윤영) 줄 커버리지는 "코드가 실행되었는가"이고 변이 점수는 "결과가 달라졌을 때 테스트가 알아채는가"라는 것을 숫자로 배웠다. AI 테스트는 assert.ok, 길이 확인, 결과로 기대값을 다시 계산하는 동어반복 때문에 코드를 실행만 하고 결과를 검사하지 않았다. 그래서 CI 기준을 정할 때도 줄 커버리지(ai_tests 97.57% vs 우리 100%)로는 약한 테스트를 막을 수 없었고, 변이 점수(58.2% vs 97.4%)를 기준으로 삼아야 했다. 실제로 ci.js 를 ai_tests 로 돌리면 테스트와 줄 커버리지는 통과하고 변이 점수 단계에서만 막혔다.
- (곽민주) 

3. 에이전트가 틀렸거나 약한 테스트를 만든 순간은? 우리는 어떻게 알아챘고 어떻게 바로잡았나요?
- (김윤영) 경계값 점검에서 에이전트가 자동 취소 경계를 29 · 30 · 31분처럼 분 단위로 제시했다. 계약서의 "30분 이상"과 문제지 부록을 대조해 1,799,999ms · 1,800,000ms 의 밀리초 경계로 바꿨다. 또 계약서에 정의되지 않은 page 0 을 경계값으로 넣어, 원본 코드에서 실패할 위험이 있어 제외했다.
- (김윤영) flaky 수정 제안에서 에이전트가 real_clock 의 29ms · 30ms 를 테스트 이름과 거꾸로 짝지었고, shared_state 의 '두 번째 구매자의 주문번호는 ORD-0002' 테스트가 ORD-0001 을 확인하도록 제안했다. AI 테스트 리뷰 때 정리한 체크리스트 5번(테스트 이름과 단언이 일치하는가)으로 읽어서 알아챘고, 고치기 전에 계획을 수정해 내비게이터의 승인을 받았다.
- (김윤영) 에이전트를 써서 작성된 검증 보고에 "확인 필요" 같은 실행하지 않은 표현과, 테스트 내용과 맞지 않는 실패 메시지가 섞여 있었다. 터미널 출력 원문을 다시 받아 확인했다. 에이전트의 "통과했다"는 보고도 그대로 믿지 않고, 커밋 전에 사람이 npm test 를 직접 한 번 더 돌렸다.
- (곽민주) 

4. 불안정 테스트의 원인을 찾은 과정에서 가장 도움이 된 것은?
- (김윤영) npm run repeat 의 실패 예시 메시지가 가장 도움이 되었다. random_quantity 는 실패가 모두 OUT_OF_STOCK 이라 무작위 수량 11 이 재고 10 을 넘는다는 것을 바로 알 수 있었고, shared_state 는 기대 ORD-0001 / 실제 ORD-0002 처럼 번호가 뒤바뀌어 공유 ctx 와 동시 실행이 원인임을 알았다. real_clock 은 '방금 만든 주문'이 취소되는 실패로 실제 시계와 무작위 지연이 30ms 경계를 넘나든다는 것을 확인했다. 고친 뒤에는 30회 · 100회 반복이 모두 0% 였고, 실패율보다 "비결정적인 원인을 코드에서 없앴다"는 것을 더 강한 근거로 보았다. real_clock 은 정확히 30ms 경계를 확인하게 되어 고치기 전보다 더 강한 테스트가 되었다.
- (곽민주) 

5. AGENTS.md(규칙 파일)에 실습 중에 추가하거나 고친 규칙이 있다면?
- Mission 0 에서 팀 규칙 1~3: 검증자가 일부러 틀린 값으로 실패를 확인한 뒤 승인, 에이전트는 작업마다 git status 를 보고하고 src · ai_tests 변경 시 되돌림, 커밋 전 npm test 3회 실행.
- Mission 2 에서 팀 규칙 4: 실패할 수 없는 테스트 금지 — try/catch 대신 expectCode / expectRejectCode, 기대값은 계약서로 미리 계산한 숫자, 테스트 이름이 약속한 값은 반드시 단언. ai_tests 리뷰에서 찾은 약점을 다시 만들지 않기 위해 추가했다.
- Mission 4 에서 팀 규칙 5: 무작위 값은 유효 범위 전체를 순회하거나 시드 고정, 공유 ctx · concurrency 금지, 새 테스트는 repeat 30회 확인. flaky 3개의 원인을 처음부터 막기 위해 추가했다.
- 규칙 3(npm test 3회)은 에이전트가 AGENTS.md 를 읽고 스스로 지켰다. 규칙 파일이 실제로 에이전트의 행동을 바꾼다는 것을 확인했다.
- (곽민주) 

6. 다음에 AI 와 테스트를 만들 때 바꿀 점 한 가지는?
- (김윤영) 처음부터 "케이스 목록 먼저 → 사람 승인 → 코드" 순서와, 출력형식에 "처음 실행에서 실패했다가 고친 것"을 넣겠다. 중간부터 이 항목을 넣었더니 에이전트가 import 누락을 스스로 고친 것까지 숨기지 않고 보고했다. 또 프롬프트를 [목표] / [컨텍스트] / [제약조건] / [출력형식]으로 나누어 쓰고, 에이전트가 자주 틀리는 부분(밀리초 경계, 정의되지 않은 동작, 이름과 단언 일치)은 제약조건에 미리 적는 것이 효과적이었다.
- (곽민주) 

7. (선택) 이 실습의 문제 · 계약서에서 모호했던 부분은?
- 계약서 1장 3번의 maxAddable "지금 더 담을 수 있는 최대 수량"이 changeQuantity 에서는 "더 담을 수 있는 양"과 "바꿀 수 있는 최대 수량" 두 가지로 읽혔다. 팀이 "재고"로 해석하는 가정을 PLAN.md 5절에 적고 진행했다(TC-R-15).
- 자동 취소의 경계가 SRS 에는 "30분이 지난", 계약서에는 "30분 이상"으로 표현되어 정확히 30분일 때의 동작을 계약서 기준으로 정했다.
- 주문 목록의 page 0 처럼 계약서에 정의되지 않은 입력은 테스트하지 않기로 했다.
