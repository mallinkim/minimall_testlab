## 3. 커버리지가 높은데 변이 점수가 낮았던 이유 (우리 팀의 결론)
- 줄 커버리지는 "그 줄이 실행되었는가"만 보고, 변이 점수는 "코드가 틀리게 바뀌었을 때 테스트가 알아채는가"를 본다. ai_tests는 39개가 모두 통과하고 줄 커버리지가 97.57%였지만 변이 점수는 58.2%(110/189)였다.
- 원인은 코드를 실행만 하고 결과는 검사하지 않는 테스트였다. try/catch로 오류를 삼켜 오류가 나지 않아도 통과하는 테스트(결제 실패를 성공 처리하는 payment#10·#13, 취소된 주문 결제를 허용하는 payment#21이 살아남음), 결과로 기대값을 다시 계산하는 동어반복(합계 계산을 나눗셈으로 바꾼 cart#38이 살아남음), 이름은 "재고를 복원한다"인데 재고를 확인하지 않는 테스트였다.
- 우리 테스트도 줄 커버리지는 Mission 2 때 이미 100%였지만 변이 점수는 92.1%였고 15개가 살아남았다. 남은 15개는 동시 요청, 환불 예외, 남의 주문, 자동 취소의 상태 조건처럼 "한 번 실행해 본 것"으로는 보이지 않는 규칙이었다. 이 15개 중 12개는 규칙마다 별도 테스트를 추가해 죽였고, 점수가 오른 단계는 모두 살아남은 변이체와 연결된 테스트를 쓴 단계였다.
- 그래서 우리 CI 기준도 줄 커버리지(ai_tests 97.57%와 my_tests 100%로 구분 불가)가 아니라 변이 점수(58.2%와 98.4%)로 막기로 했다. 반대로 점수가 오르지 않은 단계(재시도, 이미 결제됨, 남의 주문 등)도 계약 규칙을 지키는 테스트이므로 유지했다. 점수는 약한 테스트를 찾는 도구이고, 점수만으로 테스트의 가치를 판단하지는 않았다.

## 4. 한계와 남은 위험 (3가지)
1. **계약서에 없는 동작을 팀 가정으로 채운 테스트와 남겨 둔 생존 3개.** 결제 id 형식(payment#5, #6)과 삭제된 상품이 있는 장바구니 조회(cart#35)는 기대 동작을 정할 근거가 없어 테스트하지 않았다. 반대로 "서로 다른 결제 기록의 id는 달라야 한다", "삭제된 상품이 있어도 취소는 성공한다", "주문이 없으면 `items: []`", 환불 실패 시 결제 status 같은 값은 팀 가정으로 테스트에 넣었다. 숨은 결함이 이런 계약의 빈칸에 있다면 놓칠 수 있고, 팀 가정이 실제 의도와 다르면 테스트가 틀린 쪽이 된다.
2. **저장소 구조(`ctx.store`)에 기댄 확인.** 상품 가격 변경·삭제, 결제 기록 읽기, 자동 취소 뒤 재고 확인은 `ctx.store.products`, `ctx.store.payments`, `ctx.store.orders`를 직접 읽거나 고친다. 계약서가 저장소 구조를 공개해 허용했지만, 구조가 바뀌면 테스트가 함께 깨지고 "구현에 맞춘 테스트"가 될 위험이 있다.
3. **변이 도구와 동시성 테스트의 범위.** 98.4%는 도구가 만든 189개 변이에 대한 점수이지, 모든 결함을 잡는다는 뜻이 아니다(복합 조건, 도구가 만들지 않는 종류의 결함은 점수에 나타나지 않는다). 또 동시 요청·동시 취소 테스트는 제어형 스텁과 `setImmediate`로 호출이 겹치는 순서를 만들어 내는데, 이벤트 루프의 실행 순서에 기대는 방식이라 환경이 바뀌면 흔들릴 수 있다. 그래서 새 테스트는 `npm run repeat -- my_tests --times 30`으로 반복해 확인한다.
