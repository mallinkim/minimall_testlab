# 불안정(flaky) 테스트 기록 (Mission 4)

측정: `npm run repeat -- flaky_tests/<파일>.test.js --times 30`

| 테스트 파일 | 수정 전 실패율 | 원인 가설 | 확인한 근거(어떻게 알았나) | 고친 방법 | 수정 후 실패율(30회 이상) |
|---|---|---|---|---|---|
| random_quantity.test.js | 23.3% (7/30) | 무작위 — 수량을 1~11 중 무작위로 뽑는데 P1 재고가 10이라, 11이 뽑히면 재고 부족 오류가 남 | repeat 30회의 실패 메시지가 모두 OUT_OF_STOCK. 코드에서 Math.random() * 11 + 1 (최대 11) 확인, seed.js 의 P1 재고 10 과 계약서 장바구니 3번 대조 | 무작위 대신 유효 수량 1~10 을 모두 순회하고 수량마다 새 컨텍스트 사용. 테스트 2개 · 단언 유지, 오히려 더 많은 값을 검사 | 0% (0/30) |
| real_clock.test.js | 50% (15/30) | 실제 시간 — 실제 시계와 무작위 지연(sleep 20 + jitter 0~30, jitter 0~40)이 30ms 경계를 넘나듦 | 실패 메시지: '방금 만든 주문' 기대 [] / 실제 ['ORD-0001'], '30ms 지난 주문'은 반대로 취소되지 않음. createContext() 기본 시계가 실제 시간임을 testkit 에서 확인 | createFakeClock 으로 바꾸고 '자동 취소된다'는 정확히 30ms, '아직 취소되지 않는다'는 29ms 진행. jitter 는 남겨 두어도 가짜 시계라 결과가 바뀌지 않음. 경계(30ms 이상)를 정확히 확인하게 되어 테스트가 더 강해짐 | 0% (0/30) |
| shared_state.test.js | 40% (12/30) | 공유 상태 · 실행 순서 — 파일 맨 위 ctx 하나를 두 테스트가 함께 쓰고 concurrency: true 로 동시에 실행되어, 주문 순서에 따라 번호가 뒤바뀜 | 실패 메시지: 기대 ORD-0001 / 실제 ORD-0002 (두 번째 테스트는 반대). 코드에서 공유 ctx 와 concurrency: true, jitter 확인 | 테스트마다 새 컨텍스트. '두 번째 구매자 ORD-0002'는 한 테스트 안에서 u1 주문 후 u2 주문으로 순서를 명시. 동시 실행 · jitter 제거. 테스트 2개 · 단언 유지 | 0% (0/30) |

## 원인 유형 정리 (팀이 직접 쓴다)
- 무작위 · 시간 · 실행 순서 · 공유 상태 · 외부 시스템 중 우리가 만난 원인은? 무작위(random_quantity), 실제 시간(real_clock), 공유 상태 + 실행 순서(shared_state). 세 가지 모두 테스트 코드 쪽 문제였고 src 는 바꾸지 않았다.
- 앞으로 불안정 테스트를 예방하려고 AGENTS.md 에 추가할 규칙은? 팀 규칙 5 — 무작위 값은 계약상 유효한 범위 전체를 순회하거나 시드를 고정하고, 테스트 간에 ctx 를 공유하거나 동시 실행(concurrency)을 쓰지 않으며, 새 테스트는 npm run repeat 로 30회 확인한다.
